# 任务：为 Lance 读写流程增加元数据性能埋点

## 1. 背景与目标

我正在开展一个关于湖表元数据管理性能的研究，需要对 Lance 的读写流程进行性能分析，并与 Apache Iceberg 以及我们实现的数据库原生元数据管理方案进行比较。

请基于当前仓库中的 Lance 源码，分析其读写流程，并在其中与湖表元数据操作相关的关键位置增加性能埋点。

本次修改的目标是：

1. 识别 Lance 读取和写入过程中涉及的表级元数据操作。
2. 分别测量各个元数据阶段的执行耗时。
3. 统计一次完整读写操作中元数据处理的总耗时。
4. 输出结构化的性能数据，方便后续通过 Python 脚本进行实验分析。
5. 尽可能保持对原有 Lance 业务逻辑和性能行为的影响最小。

**本次任务只需要修改源码增加埋点，不需要重新设计 Lance 的元数据管理机制。**

## 2. 元数据范围定义（非常重要）

本实验中的“元数据”特指 Lance 湖表格式层面的元数据，不包括数据文件内部的元数据。

### 2.1 需要统计的操作

包括但不限于：

- 数据集最新版本的发现与解析。
- 指定历史版本的定位与解析。
- Manifest 文件的位置查找、读取和反序列化。
- Manifest 中的数据集结构、版本及 Fragment 描述信息解析。
- Fragment 元数据的获取、遍历、筛选及组织。
- 数据集 Schema 等表级元数据的解析。
- 写入过程中新版本 Manifest 的构造、序列化和持久化。
- 数据集版本的提交、发布及相关元数据更新。
- 写入过程中必要的版本校验与冲突检测。

以上是逻辑阶段，不要求严格按这些名称划分。请以当前版本的真实源码调用链为依据，确定最终埋点位置。

### 2.2 严格排除的操作

以下操作不计入元数据统计：

- `.lance` 数据文件的实际读取与写入。
- 数据文件内部的 Footer、Page、Column 等元数据的解析。
- 数据文件内部的编码、解码、压缩、解压缩。
- Arrow RecordBatch 的构造和处理。
- 实际的数据扫描、过滤、投影和计算。
- 向量索引或其他数据索引内部结构的读取及搜索。
- 数据文件的生成、上传和持久化。

需要特别注意，Fragment 元数据属于本次统计范围，但根据 Fragment 定位到 `.lance` 数据文件之后，对数据文件内部结构的读取不属于统计范围。

如果某个函数同时包含元数据操作和数据文件操作，请在函数内部进行更细粒度的埋点，不能简单地把整个函数耗时当作元数据耗时。

## 3. 需要分析的读写场景

### 3.1 读取最新版本（Full Scan）

典型流程：

1. 打开 Lance Dataset。
2. 定位最新版本。
3. 加载并解析 Manifest。
4. 获取当前版本包含的 Fragment 信息。
5. 构造全量扫描所需的元数据结构。

本实验只关心到扫描所需的元数据准备完成为止，不关心后续实际扫描数据文件的耗时。

### 3.2 读取历史版本（Time Travel）

典型流程：

1. 根据指定版本号定位历史版本。
2. 加载对应版本的 Manifest。
3. 解析该版本的 Schema 和 Fragment 信息。
4. 准备历史版本的扫描元数据。

需要区分历史版本定位耗时与 Manifest 加载耗时。

### 3.3 带过滤条件的读取（Filter Scan）

典型流程：

1. 定位 Dataset 版本。
2. 加载 Manifest。
3. 解析 Fragment 信息。
4. 根据可用的表级元数据或统计信息，完成能够在数据文件读取前执行的 Fragment 筛选或扫描规划。

请特别注意：

- 只统计实际发生在数据文件读取之前的表级元数据处理。
- 如果过滤条件依赖 `.lance` 文件内部统计信息，该部分读取和解析不纳入本次元数据统计。
- 如果 Lance 无法仅依靠表级元数据完成 Fragment 筛选，请如实说明，不要假设一定存在该阶段。
- 不统计实际的 Filter 执行耗时。

### 3.4 数据写入（Append / Insert）

典型流程：

1. 执行数据写入。
2. 收集新生成的数据文件及 Fragment 描述。
3. 读取或确认当前 Dataset 版本。
4. 构造新版本的元数据。
5. 生成并持久化新的 Manifest。
6. 执行版本提交与发布。

只统计其中的元数据管理操作。

特别注意：生成 Fragment 描述信息属于元数据相关操作，但实际写入数据文件不属于元数据操作。

如当前实现中还存在 Transaction 文件、版本更新或并发控制相关元数据操作，也需要分析是否纳入统计。

## 4. 埋点设计要求

### 4.1 先分析源码，再修改

请首先定位：

- Dataset Open / Checkout 的入口。
- 最新版本和历史版本的解析路径。
- Manifest 的读取与解析路径。
- Fragment 元数据的加载与遍历路径。
- Scanner 构建及过滤规划的相关路径。
- Append / Insert 的写入入口。
- Manifest 构建与写入路径。
- Commit、版本校验和冲突检测路径。

先给出真实的调用链、源码路径、关键函数及拟定的埋点方案，然后再实施修改。

不要根据概念上的流程直接猜测函数名称或埋点位置。

### 4.2 埋点指标

建议至少包含以下指标，最终以实际源码为准。

读取相关：

- `version_resolution`
- `manifest_location_resolution`
- `manifest_read`
- `manifest_deserialization`
- `fragment_metadata_processing`
- `schema_metadata_processing`
- `scan_metadata_planning`

写入相关：

- `write_version_validation`
- `fragment_metadata_generation`
- `manifest_construction`
- `manifest_serialization`
- `manifest_write`
- `commit_metadata_processing`
- `conflict_detection`

如果某个阶段在当前 Lance 版本中不存在，或者与其他阶段不可分割，请调整指标设计并说明原因，不要添加没有实际意义的埋点。

### 4.3 耗时测量

- 使用 Rust 的 `std::time::Instant` 等单调时钟。
- 记录 Wall-clock Duration，单位为微秒（us）。
- 对异步操作，需要覆盖实际的 `await` 执行过程。
- 避免在计时区间中加入日志格式化、性能结果文件写入等额外操作。
- 对可能重复执行的阶段，记录调用次数和累计耗时。
- 注意正确处理错误返回路径，避免计时数据丢失。
- 埋点不应改变现有异步执行、锁定、提交和错误处理语义。

### 4.4 统计口径与嵌套调用

需要避免重复统计。

例如，假设 Manifest 加载函数内部包含：

1. 位置解析。
2. 对象存储读取。
3. Manifest 反序列化。

如果同时对整个函数和三个子阶段计时，不能直接将所有耗时相加作为总耗时。

请区分：

- End-to-end Wall-clock Latency。
- 各子阶段耗时。
- 可加总的非重叠元数据耗时。

对于具有父子包含关系的指标，请明确指出。

异步并发操作也不能简单地将各阶段耗时求和并作为端到端延迟。

**最终希望得到准确、可解释、无重复计算的元数据耗时。**

## 5. 埋点实现方式

请优先采用轻量化、可维护、侵入性较低的实现。

建议：

1. 封装统一的计时工具，减少重复代码。
2. 通过环境变量或 Feature Flag 控制是否启用元数据性能采集。
3. 默认关闭，关闭时尽量做到低开销。
4. 每次 Dataset 操作拥有独立的统计上下文，避免并发读写时数据混淆。
5. 不要使用会将不同请求混合统计的单一全局计数器。
6. 尽可能兼容已有的日志和 tracing 机制。
7. 不添加与实验无关的复杂依赖。

如果操作上下文难以贯穿整个调用链，请优先提出最小侵入的可靠实现，而不是大量修改公开 API。

## 6. 输出格式

希望实验数据以 JSON Lines 格式输出，每次操作输出一条记录。

例如：

```json
{
  "operation": "read_latest",
  "dataset": "example_dataset",
  "version": 100,
  "fragment_count": 2000,
  "metadata_total_us": 1250,
  "phases": {
    "version_resolution": 120,
    "manifest_read": 450,
    "manifest_deserialization": 250,
    "fragment_metadata_processing": 300,
    "scan_metadata_planning": 130
  }
}
```

上述字段和数值仅为示例，不代表 Lance 的实际执行流程。

输出时应尽可能包含：

- operation
- dataset
- version
- fragment_count
- 各阶段累计耗时
- 各阶段调用次数
- 元数据总耗时
- 操作是否成功

对于尚未执行或不存在的阶段，不要填入虚构耗时。

允许根据 Lance 的实际实现适当调整 JSON Schema，但需要保证结构清晰、便于自动化分析。

## 7. 正确性与性能要求

修改后必须保证：

1. Lance 原有的读取、写入和版本管理行为不变。
2. 不修改 Manifest 文件格式及数据文件格式。
3. 不改变正常读写操作的执行顺序及并发语义。
4. 埋点逻辑不得影响事务提交正确性。
5. 禁用埋点时不额外产生性能结果文件。
6. 同一操作在重复测试中使用一致的统计口径。
7. 元数据总耗时不应包含实际数据文件 IO。

请尽可能通过已有测试和新增的轻量测试验证。

## 8. 交付内容

完成后请提供：

1. Lance 读写元数据调用链分析。
2. 修改过的文件列表。
3. 每个埋点对应的函数、源码位置和统计含义。
4. 完整的埋点指标表。
5. 如何启用、关闭埋点。
6. 如何运行读取最新版本、历史版本、过滤读取及 Append 写入测试。
7. JSONL 输出示例。
8. 如何计算元数据总耗时，以及如何避免重复统计。
9. 哪些元数据相关操作无法独立测量，以及原因。

不要只添加一些宏观计时器。目标是得到能用于学术实验的、阶段边界明确且可复现的元数据性能数据。

## 9. 执行顺序

请按照以下顺序完成：

第一步：阅读源码，确定实际调用链与元数据统计边界。

第二步：设计最小侵入的埋点方案与统一的输出格式。

第三步：实现读取相关埋点。

第四步：实现写入和提交相关埋点。

第五步：编译、运行相关测试并修复问题。

第六步：总结最终的指标、统计边界以及实验使用方法。

请先完成第一步并输出调用链及埋点设计，再进行源码修改。
